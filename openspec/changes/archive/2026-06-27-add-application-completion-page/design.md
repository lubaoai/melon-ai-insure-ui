## 背景

現在、保険申込みフローはステップ①〜⑤（重要事項同意→意向確認→申込内容入力→申込内容確認→決済手続き）まで実装済みであり、ステップ⑥の申込完了画面が未実装である。決済手続き画面の「次へ」ボタンは現在コンソールログを出力するのみで、申込完了画面への遷移が行えない。本変更ではステップ⑥の申込完了画面を新規追加し、既存フローと統合する。

画像UIに基づく申込完了画面の構成：
- 完了メッセージセクション（受付番号付き）
- 申込内容確認セクション（契約コース・保険料の表示）
- トップページへ戻るリンク

既存コードベースのパターン：
- ページコンポーネントは `src/app/views/` に配置
- セクションコンポーネントは機能単位で `src/components/<feature>/` に配置
- 状態管理は Zustand ストアで一元管理
- ステップナビゲーションは `StepNavigation` に `currentStep` を渡す方式

## 目標 / 非目標

**目標：**
- 決済手続き画面から遷移する申込完了画面を実装する
- 申込み完了のメッセージと受付番号を表示する
- 契約コース・保険料の確認表示を実装する
- トップページへの戻りナビゲーションを提供する
- 既存の UI コンポーネント・デザインパターンとの一貫性を保つ
- TDD でテストを先行して作成する

**非目標：**
- 実際の決済処理・受付番号のサーバー発行
- 申込内容のPDFダウンロード・メール送信
- 申込みのキャンセル機能

## 主要な決定

### 1. 受付番号の生成方式

**決定**: クライアント側でタイムスタンプベースの受付番号を生成する

**理由**: 本番環境ではサーバーから受付番号が発行されるが、現在はモック/開発段階であり、一意な番号をクライアント側で生成できれば十分。形式は `YYYYMMDD-XXXXXX`（日付-6桁乱数）とし、視覚的に受付番号らしい形式とする。

**代替案**: 固定のダミー番号を使用する
→ 却下理由: 毎回同じ番号ではテストやデモが不自然になる。

### 2. 申込完了画面のレイアウト

**決定**: 完了画面は他のステップ画面と異なり、サイドバーなしの単一カラムレイアウトとする

**理由**: 画像UIに基づき、完了画面は情報表示のみで入力がないため、Q&Aサイドバーは不要。完了メッセージと申込内容確認を中央に配置するすっきりとしたデザインとする。

**代替案**: 他のステップと同様にサイドバー付きレイアウト
→ 却下理由: 完了画面は操作が不要な最終画面であり、ユーザーの注意を完了メッセージに集中させる方が適切。

### 3. 申込内容確認セクションの表示内容

**決定**: 契約コース（保険期間・支払方法・商品・プラン種別）と保険料合計のみを表示する

**理由**: 画像UIに基づき、完了画面では主要な契約情報のみを簡潔に表示する。全入力項目の再表示は申込内容確認画面（ステップ④）で既に実施済み。

### 4. トップページへのナビゲーション

**決定**: 「トップページへ戻る」リンクを `NavigationButtons` ではなく独立したリンクとして表示する

**理由**: 完了画面には「戻る」ボタンが不要（申込みは完了済み）。画像UIに基づき、「トップページへ戻る」テキストリンクを配置する。

### 5. コンポーネント構成

**決定**: `src/components/completion/` ディレクトリに以下のコンポーネントを配置する

- `CompletionMessageSection` - 完了メッセージと受付番号
- `CompletionSummarySection` - 契約コース・保険料の確認表示

**理由**: 確認画面のセクション構成パターンと同様に、機能単位でコンポーネントを分割する。

## リスクとトレードオフ

- **[受付番号の一意性]** クライアント側の乱数生成では衝突の可能性がある → 本番移行時にサーバー発行に変更する前提であり、現在は表示目的のみ
- **[戻るボタンでの再遷移]** ユーザーがブラウザの戻るボタンで決済手続き画面に戻った場合、再度「次へ」を押すと新しい受付番号が発行される → 決済手続き画面の `useEffect` でストアに `isCompleted` フラグを設定し、完了済みの場合は完了画面にリダイレクトする設計とする
