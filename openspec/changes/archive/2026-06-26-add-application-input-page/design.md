## 背景

現在、生命保険申込フローのステップ①（重要事項同意）とステップ②（意向確認）まで実装済み。ステップ③の申込内容入力画面が未実装であり、意向確認画面の「次へ」ボタンはコンソールログ出力のみのプレースホルダー状態。本変更では、実際のWeb申込画面（メロン少額短期保険）のHTML構造に基づき7セクション構成の申込入力画面を新規実装し、既存のデザインシステム・共通コンポーネントを活用して画面遷移を繋ぐ。

既存のアーキテクチャパターン：
- ページコンポーネントは `src/app/views/` に配置
- セクションコンポーネントは `src/components/<feature>/` に配置
- ルーティングは React Router 7 の `Routes`/`Route` で定義（`src/router/index.tsx`）
- ページレイアウトは StepNavigation + メインコンテンツ + QASidebar の3カラム構成
- 入力フィールドは `border border-border bg-label-bg` のラベル + `border border-l-0 border-border bg-input-bg` の入力エリアのペアパターン

## 目標 / 非目標

**目標：**
- 申込内容入力画面を実際のHTML構造に基づく7セクション構成で実装する
- 既存のデザインシステム（Tailwind CSS カスタムプロパティ）と共通コンポーネントを再利用する
- 意向確認画面からの画面遷移を有効化する
- 条件付き表示（法人選択時の追加フィールド、契約者と異なる選択時の居住者詳細、同居人あり選択時の同居人入力）を実装する
- TDDサイクルに従い、テストファーストで実装する

**非目標：**
- API連携・サーバーへのデータ送信は行わない（モックデータのみ）
- 郵便番号からの住所自動補完機能は実装しない（住所検索ボタンは表示のみ）
- カレンダーピッカー（datepicker）は実装せず、テキスト入力で代用する
- 動的保険料計算は実装しない（固定値表示）
- フォームの状態管理にZustand等の外部ストアは導入しない（Reactのローカルstateで管理）
- 次画面（④申込内容確認）の実装はスコープ外

## 主要な決定

### 1. フォーム状態管理: Reactローカルstate

**決定**: 各セクションコンポーネントでローカルstateを管理し、ページコンポーネントで統合する。

**理由**:
- 申込入力画面は単一ページ内で完結するフォームであり、複数ページ間で状態を共有する必要がない
- 既存のIntentConfirmationPageも同じパターン（useState + コールバック）を採用している
- Zustandの導入はオーバーエンジニアリングとなる

**代替案**: Zustandストアで全フォーム状態を一元管理 → 却下。単一画面のフォームには不要な複雑性。

### 2. セクションコンポーネントの構成（7セクション）

**決定**: 実際のHTML構造に基づき7つのセクションコンポーネントを作成する。

- `ContractDateSection`: ①契約希望日（date input + 注記テキスト）
- `ContractCourseSection`: ②ご契約コース（保険期間ラジオ・支払方法ラジオ・商品ラジオ・プラン種別select・保険料・保険料種類）
- `HousingOverviewSection`: ③住居の概要（構造ラジオ・形態ラジオ・階数入力）
- `ContractorInfoSection`: ④ご契約者様の情報（契約種別ラジオ・氏名・カナ・性別・生年月日・住所・建物名・住所フリガナ・電話番号）
- `ResidenceLocationSection`: ⑤住居の所在地（「契約者と同じ」ボタン付き・住所・建物名・住所フリガナ）
- `PrimaryResidentSection`: ⑥主たる居住者（区分ラジオ・「契約者と異なる」選択時の追加フィールド）
- `CoResidentSection`: ⑦同居人の明細（同居人有無ラジオ・あり時の最大5名入力）

**理由**:
- 実際のHTMLのセクション構成に1:1で対応
- 各セクションが独立してテスト可能
- 条件付き表示のロジックを各セクション内にカプセル化できる

### 3. 条件付き表示の実装方針

**決定**: 各セクションコンポーネント内で条件付き表示を管理する。

- ④ご契約者様の情報: 契約種別「法人」選択時に法人名・法人名カナ・役職名を表示
- ⑥主たる居住者: 「契約者と異なる」選択時に居住者詳細フィールドを表示
- ⑦同居人の明細: 「あり」選択時に同居人1のフィールドを表示し、「同居人を追加」ボタンで最大5名まで追加

**理由**:
- 条件付き表示は各セクションのローカル関心事であり、ページレベルで管理する必要がない
- コンポーネント内で完結することでテストが容易

### 4. 入力フィールドパターンの再利用

**決定**: 既存のIntentionSectionで使用されている入力フィールドパターン（ラベル + 入力エリア）を各セクションに適用する。

**理由**:
- デザインの一貫性を保つため
- 画面イメージのスタイルと既存実装が一致している
- 新たなスタイル定義が不要

### 5. バリデーション方針

**決定**: 必須項目の未入力チェックとフォーマットチェックを「次へ」ボタン押下時に実行する。

**理由**:
- 実際のHTMLの「必須」バッジ表示から必須項目が明確
- 既存のIntentionSectionも「次へ」ボタンの活性/非活性で制御している
- リアルタイムバリデーションはUX的に過剰になる可能性があるため、送信時チェックとする

### 6. コンポーネント配置ディレクトリ

**決定**: 新規セクションコンポーネントは `src/components/application/` に配置する。

**理由**:
- 既存の `src/components/home/` はホーム・意向確認画面用
- 申込入力画面専用のコンポーネントであることを明確にする
- ディレクトリ名はルートパス `/application-input` に対応

## リスクとトレードオフ

- [ローカルstateでのフォーム管理は、入力項目が多い（7セクション）ためページコンポーネントのstateが肥大化する] → セクション単位でstateを分割し、各セクションが自身の状態を管理することで緩和。ページコンポーネントはバリデーション結果のみを受信する設計とする。
- [条件付き表示の入力フィールドが多いと、必須項目の判定が複雑になる] → canProceed判定関数をセクションごとに定義し、ページレベルで集約する。
- [バリデーションを「次へ」ボタン押下時にのみ実行すると、ユーザーが全項目入力後にまとめてエラーを見ることになる] → エラー箇所にスクロールする機能を検討。ただし初期実装ではエラー表示に留める。
- [ドロップダウン（プラン種別・都道府県・続柄等）の選択肢データのハードコーディング] → 現時点ではモックデータとして実装し、将来的なAPI化時にデータソースを切り替え可能な構造にする。
