## 背景

現在の申込内容入力画面は全てのフィールドが空の状態で表示される。開発・テスト・デモ用途において、毎回手動で全項目を入力する必要があり、画面遷移の確認や動作検証に手間がかかる。また、決済手続き画面と申込完了画面の保険料合計が0円のハードコードとなっており、実際の保険料が反映されていない。

各セクションコンポーネント（ContractDateSection、ContractCourseSection等）は現在、`useState`で空値を初期化しており、ストアの初期値を参照していない。ストア側も空値で初期化されているため、セクションコンポーネントとストアの両方を更新する必要がある。

## 目標 / 非目標

**目標：**
- 申込内容入力画面の各セクションにデモ用の初期値を設定する
- ストアの初期値をデモデータに変更し、セクションコンポーネントがストアの初期値を使用するようにする
- 契約希望日の初期値をシステム日付の1週間後に設定する
- 保険料880円を決済手続き画面・申込完了画面に反映する
- 住居の所在地に「契約者と同じ」ボタンの自動クリック相当の初期値を設定する

**非目標：**
- APIからの保険料取得ロジックの実装（今回はハードコード）
- 初期値の設定/クリアを切り替える機能の実装
- プロダクション環境向けの初期値制御（今回はデモ用固定値）

## 主要な決定

### 決定1：ストアの初期値を変更し、セクションコンポーネントはストアの値で初期化する

**選択：** ストアの初期値をデモデータに変更し、各セクションコンポーネントの`useState`初期値をストアのpropsから受け取る

**理由：** 各セクションコンポーネントは現在`useState('')`等でハードコードされた空値を使っており、ストアの値と同期していない。ストアの初期値をデモデータに変更するだけではコンポーネントのローカルstateが空のままになるため、コンポーネント側もストアの値で初期化する必要がある。

**代替案：**
- ApplicationInputPage側でuseEffectを使ってストアのsetterを呼ぶ → 二重レンダリングが発生し、非推奨
- ストアの初期値だけ変えてコンポーネントは変更しない → ローカルstateが空のまま同期されない

### 決定2：保険料880円をストアに保持し、各画面で参照する

**選択：** `insurancePremium: number` フィールドをストアに追加し、初期値880を設定。各画面はストアから金額を取得して表示する。

**理由：** 現在、PaymentPageとApplicationCompletionPageで`amount={0}`とハードコードされている。ストアで一元管理することで、将来的にAPIから取得した金額も同じ仕組みで表示できる。

**代替案：**
- 各画面で`amount={880}`とハードコード → 金額変更時に3箇所修正が必要
- ContractCourseSectionの保険料表示のみ変更 → 入力画面と決済・完了画面の金額ソースが分断される

### 決定3：住居の所在地の「契約者と同じ」初期値はストアの初期値で直接設定する

**選択：** residenceLocationのストア初期値に契約者と同じ住所データを直接設定する。UIの「契約者と同じ」ボタンクリックは模倣しない。

**理由：** 初期値として同じデータを入れるだけであり、ボタンクリックのロジックは別の関心事。ストアの初期値を設定する方がシンプルで、コンポーネントの自動クリックという副作用を避けられる。

### 決定4：契約希望日の1週間後を計算するユーティリティ関数を作成する

**選択：** `getDefaultContractDate()` ユーティリティ関数を作成し、ストアの初期値で呼び出す

**理由：** 日付計算をストア初期化に直接書くとテストが困難。ユーティリティ関数に分離することで、テスト可能で再利用可能になる。

## リスクとトレードオフ

- [ストアの初期値がデモ用固定値になる] → 将来的にAPIから初期値を取得する場合、ストアの初期化ロジックを変更する必要がある。ただし今回はデモ用途であり、後で変更可能。
- [契約希望日がシステム日付に依存する] → テスト実行日によって値が変わる。テストではユーティリティ関数をモックすることで対処。
- [プラン種別1Y8Cがストアの初期値に設定される] → 現在のストアではplanTypeは空文字。初期値を設定することでUIのセレクトボックスにデフォルト選択が反映される。
