## 背景

現在、保険申込みフローはステップ①〜④（重要事項同意→意向確認→申込内容入力→申込内容確認）まで実装済みであり、ステップ⑤の決済手続き画面が未実装である。申込内容確認画面の「次へ」ボタンは現在コンソールログを出力するのみで、決済手続き画面への遷移が行えない。本変更ではステップ⑤の決済手続き画面を新規追加し、既存フローと統合する。

既存コードベースのパターン：
- ページコンポーネントは `src/app/views/` に配置
- セクションコンポーネントは機能単位で `src/components/<feature>/` に配置
- 状態管理は Zustand ストア（`src/store/applicationFormStore.ts`）で一元管理
- フォーム行は `FormRow` コンポーネントで統一
- ナビゲーションは `NavigationButtons` コンポーネントを再利用
- ステップナビゲーションは `StepNavigation` に `currentStep` を渡す方式

## 目標 / 非目標

**目標：**
- 申込内容確認画面から遷移する決済手続き画面を実装する
- クレジットカード情報の入力フォームを提供する
- お支払金額の確認表示を実装する
- 決済情報を Zustand ストアで管理する
- 既存の UI コンポーネント・デザインパターンとの一貫性を保つ
- TDD でテストを先行して作成する

**非目標：**
- 実際のクレジットカード決済処理（外部決済代行サービスとの連携）
- クレジットカード番号のトークン化・暗号化
- コンビニ払い・銀行振込など他の支払方法の実装
- 申込完了画面（ステップ⑥）の実装（別 change で対応）

## 主要な決定

### 1. 決済情報の Zustand ストア追加

**決定**: 既存の `applicationFormStore` に決済情報の状態を追加する

**理由**: 既存の申込みフローが単一ストアで管理されており、決済情報も申込みデータの一部として同じパターンで管理するのが一貫性がある。ストアを分割するとデータ間の依存関係が複雑になる。

**代替案**: 決済専用の別ストアを作成する
→ 却下理由: 決済情報は申込みフローの一部であり、独立したドメインではない。単一ストアの方がシンプル。

### 2. クレジットカード情報のフォーム管理

**決定**: 各セクションコンポーネント内でローカル `useState` で管理し、変更時に `onChange` コールバックでストアに反映する

**理由**: 既存の申込入力セクション（`ContractCourseSection` 等）と同じパターン。ローカル状態で即時フィードバックを提供しつつ、ストアで永続化する。

**代替案**: フォームライブラリ（React Hook Form 等）の導入
→ 却下理由: 既存コードが全て `useState` パターンであり、この画面のみライブラリを導入すると一貫性が失われる。

### 3. 支払方法の選択肢

**決定**: 現時点では「クレジットカード払い」のみを表示し、ラジオボタンで選択状態を表現する（実質的に固定選択）

**理由**: 画像UIに基づきクレジットカード払いのみが表示されている。将来の拡張に備えてラジオボタン形式としているが、現時点では1択。

### 4. 入力バリデーション方針

**決定**: クレジットカード情報の基本的な形式バリデーションを実装する（桁数・フォーマットチェック）

**理由**: 決済情報であるため、明らかな入力ミスを防ぐ必要がある。ただし、実際のカード番号の妥当性検証（Luhn チェック等）は非目標。

**バリデーション内容**:
- カード番号: 16桁の数字
- 有効期限: 月（01-12）/ 年（現在年以降）
- カード名義人: 半角英字スペース区切り
- セキュリティコード: 3-4桁の数字

### 5. コンポーネント構成

**決定**: `src/components/payment/` ディレクトリに以下のセクションコンポーネントを配置する

- `PaymentMethodSection` - お支払方法選択
- `CreditCardSection` - クレジットカード情報入力
- `PaymentAmountSection` - お支払金額表示
- `CautionSection` - 注意事項表示（既存 `caution-section` スタイルを再利用）

**理由**: 確認画面のセクション構成パターン（`src/components/confirmation/`）と同様に、機能単位でコンポーネントを分割することで、テスト容易性と保守性を確保する。

## リスクとトレードオフ

- **[セキュリティリスク]** クレジットカード情報が Zustand ストア（メモリ）に保持される → 本番環境では決済代行サービスのトークン化を利用する設計とする。現在の実装ではカード情報を直接保持するが、これはモック/開発用であり、本番移行時にトークンベースに変更する前提
- **[データ消失リスク]** ユーザーが決済手続き画面で入力途中にブラウザをリロードした場合、ローカル状態がリセットされる → Zustand の `persist` ミドルウェアは現時点では導入せず、既存ストアパターンに合わせる
- **[拡張性の制約]** 支払方法がクレジットカードのみの固定選択 → 将来コンビニ払い等を追加する際は、ラジオボタンの選択肢を増やし、選択に応じて表示セクションを切り替える設計に拡張可能
