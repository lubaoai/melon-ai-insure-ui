# 品質レビュー

## 1. 境界条件

**ステータス**：⚠️ 警告

**発見事項**：
- カード番号の16桁超過のシナリオが未カバー（17桁以上の入力をどう扱うか）
- 有効期限の年の上限（遠未来の年入力）のシナリオが未カバー
- セキュリティコードの5桁以上の入力のシナリオが未カバー
- カード名義人に数字や記号が含まれる場合のシナリオが未カバー
- `paymentMethod` に `'credit'` 以外の値が渡された場合の挙動が未定義

**提案**：
- カード番号は16桁でmaxlength制限を設けることで超過入力を防止する設計で対応可能（spec側の追記は任意）
- 有効期限の年は現在年+10年程度の範囲制限を設けることを推奨
- セキュリティコードは4桁が上限（Amex）のためmaxlength=4で制御
- カード名義人のバリデーションルールを明確化（半角英字＋スペースのみ許容）
- 現時点では支払方法は1択のため、`paymentMethod` の他値の挙動は将来拡張時に定義で問題なし

## 2. ロールバック方案

**ステータス**：✅ 合格

**発見事項**：
- 本変更は新規画面の追加と既存画面の遷移先変更のみであり、データ移行を伴わない
- `applicationFormStore` への状態追加は後方互換（既存フィールドに影響なし）
- 申込内容確認画面の「次へ」ボタンの遷移先変更は単純なURL変更であり、ロールバックは1行の差し戻しで可能
- ルーティング追加もRoute要素の削除で容易にロールバック可能

**提案**：
- 特になし。リスクの低い変更であり、ロールバック戦略は不要

## 3. テストカバレッジ

**ステータス**：✅ 合格

**発見事項**：
- 全てのシナリオが WHEN/THEN 形式で明確に記述されており、テストケースとして直接変換可能
- クレジットカード情報の異常系（空値・短すぎ・非数値）が3パターン以上カバーされている
- ページレベルのテスト（ルーティング・リダイレクト・レイアウト）とコンポーネントレベルのテストが分離されている
- design.md で TDD サイクルが明記されており、テスト先行が担保される

**提案**：
- 各セクションコンポーネントのテストに加え、`PaymentPage` 全体の統合テスト（全フィールド入力→次へボタン有効化→クリック）を1テストファイルに含めることを推奨

## 4. 後方互換性

**ステータス**：✅ 合格

**発見事項**：
- `applicationFormStore` の既存フィールド・アクションに影響なし。新規フィールドの追加のみ
- 既存のコンポーネント（`FormRow`, `NavigationButtons`, `StepNavigation`, `QASidebar`, `ScrollTopButton`）は全て再利用であり、インターフェース変更なし
- `ApplicationConfirmationPage` の変更は `handleNext` 内の `console.log` から `navigate('/payment')` への変更のみ
- 新規ルート `/payment` の追加は既存ルートに影響なし

**提案**：
- 特になし。後方互換性への影響は最小限

## 全体評価

全体的に well-structured な仕様であり、リスクの低い新規追加変更である。境界条件に一部未カバーの箇所があるが、実装時のmaxlength/input制限で対応可能なレベル。

**分割方向の提案**：

タスクは以下のグループに分割する：

1. **データ層グループ**：`CreditCardInfoData` 型定義 + Zustand ストア拡張（他の全タスクの前提）
2. **セクションコンポーネングループ**：各セクションを1タスクずつ作成（PaymentMethodSection → CreditCardSection → PaymentAmountSection → CautionSection）
3. **ページ統合グループ**：PaymentPage 作成 + ルーティング追加 + ApplicationConfirmationPage の遷移先変更

**優先順位付け**：

1. `CreditCardInfoData` 型 + ストア拡張（最優先：全コンポーネントが依存）
2. `PaymentMethodSection`（最もシンプル、パターン確立）
3. `CreditCardSection`（最も複雑、バリデーション含む）
4. `PaymentAmountSection` + `CautionSection`（表示のみ、独立）
5. `PaymentPage` + ルーティング（統合、最後に配置）
6. `ApplicationConfirmationPage` の遷移先変更（1行変更、最後に実施）

**粒度の基準**：

- 各タスクは1コンポーネントまたは1ファイルの変更に相当する単位
- テスト作成→実装→確認のサイクルが1タスク内で完結する粒度
- CreditCardSection はバリデーションが複雑なため、入力フィールド表示→バリデーション追加の2タスクに分割する可能性があるが、まずは1タスクで実施し進行に応じて分割を検討
