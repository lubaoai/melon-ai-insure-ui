## 背景

Melon AI Insure UI リポジトリは空の初期状態であり、開発に必要なフロントエンド基盤が存在しない。技術スタックとして React 19 + TypeScript + Vite + Tailwind CSS 4 + React Router 7 が決定しており、Zustandによる状態管理とVitestによるテストを前提としている。ステークホルダーは開発チームのみであり、既存システムとの統合は発生しない。APIが未実装であるため、ブラウザレベルでネットワークリクエストを模倣するモック環境が求められている。

## 目標 / 非目標

**目標：**
- Vite + React 19 + TypeScript + Tailwind CSS 4 の高速SPA環境を構築し、すぐに機能開発を開始できるようにする
- 役割を明確に分けたスケーラブルなディレクトリ構造（`app/views`, `app/layouts`, `modules`, `router`, `lib`）を採用する
- React Router 7 によるルーティング基盤を確立し、ルーター設定を `router/` ディレクトリに集約する
- MSWを導入し、本番に近い開発体験（ブラウザレベルのAPIモック）を実現する
- HomePageでモックAPI経由で保険商品一覧を描画し、画面表示の基盤を完成させる
- OpenSpec連携の設定ファイルとテンプレートを初期から組み込み、品質管理を自動化する

**非目標：**
- 本番APIとの接続（MSWモックのみ）
- 認証・認可機能の実装
- レスポンシブデザインの完全な最適化
- 国際化（i18n）対応
- CI/CDパイプラインの構築

## 主要な決定

### 1. バンドラとしてViteを選択
**決定**: Viteをバンドラとして採用する
**理由**: HMRの高速さ、ESMネイティブサポート、React 19との互換性
**代替案**: Webpack（設定が複雑で開発体験が劣る）、Turbopack（まだ安定版でない）

### 2. React Router 7をルーティングに採用
**決定**: react-router-dom v7をルーターとして使用する
**理由**: React生態界のデファクトスタンダード、データローディング機能、ネストルート対応
**代替案**: TanStack Router（型安全性は高いが学習コストが大きい）、Next.js（SSR不要で過剰）

### 3. Tailwind CSS 4でスタイリング
**決定**: Tailwind CSS v4をスタイリングソリューションとして使用する
**理由**: ユーティリティファーストアプローチによる開発速度向上、@tailwindcss/viteによるVite統合
**代替案**: CSS Modules（スケール時の管理コスト）、styled-components（ランタイムオーバーヘッド）

### 4. MSW (Mock Service Worker) によるAPIモック
**決定**: MSWを導入し、ブラウザのService WorkerレベルでAPIリクエストを模倣する
**理由**: 本番と同じネットワークレイヤーでテスト可能、fetchインターセプトによりコンポーネントコードの変更なしにAPI移行可能、開発・テスト両環境で利用可能
**代替案**: 静的TypeScriptファイル（コンポーネントが直接データに依存しAPI移行時の変更が大きい）、JSON Server（別プロセス起動が必要）、MirageJS（MSWより採用実績が少ない）

### 5. スケーラブルなディレクトリ構造
**決定**: `app/views`, `app/layouts`, `modules`, `router`, `lib` の役割別ディレクトリ構造を採用する
**理由**: 各ディレクトリの役割が明確で、機能追加時の迷いがない。modulesにドメインロジックを集約し、app/にUI層を分離することで関心事の分離が実現できる
**代替案**: Flat構成（機能増加時に破綻）、Feature-based構成（初期段階では過剰、modules内で部分的に採用可能）

**ディレクトリ構造:**
```
src/
├── app/
│   ├── views/        # ページコンポーネント（HomePage等）
│   └── layouts/      # レイアウトコンポーネント
├── modules/          # ドメインモジュール（型、API呼び出し、ビジネスロジック）
├── router/           # ルーティング設定
├── lib/              # ユーティリティ、共有ライブラリ
├── mocks/            # MSWハンドラ、ブラウザワーカー設定
└── main.tsx          # エントリーポイント
```

### 6. OpenSpec連携の初期組み込み
**決定**: OpenSpecの config.yaml とレビューテンプレートをプロジェクト初期から組み込む
**理由**: 品質管理の自動化を開発初期から実践し、後からの組み込みコストを回避する
**代替案**: 品質管理ツールなし（手動レビューのみ、属人的）、後からの導入（移行コストが大きい）

## リスクとトレードオフ

- [MSWのService Workerが古いブラウザで動作しない可能性] → ターゲットブラウザがモダンブラウザのみであるため影響なし。開発環境でのみ使用するため本番への影響もなし
- [モックデータと本番APIの切り替え方法] → MSWは開発時のみ有効化し、本番ビルドではMSWを含めない設計とする。APIクライアント層はmodulesに集約し、MSW無効化でシームレスに本番APIへ移行可能
- [React Router 7の破壊的変更リスク] → v7は安定版であるためリスクは低いが、アップデート時の変更履歴を監視する
- [modules内のドメイン分割基準が不明確になる可能性] → 初期はproducts単位で分割し、機能増加に応じて再編する方針とする
