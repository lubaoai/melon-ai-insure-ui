## 背景

現在、申込入力画面（ApplicationInputPage）で7セクションのフォームデータが各useStateで管理されている。申込内容確認画面を追加するにあたり、入力画面で入力されたデータを確認画面で表示する必要がある。既存のコードベースではページ間のデータ引き渡しはReact Routerのnavigateのみで行われており、グローバルな状態管理は導入されていない。

## 目標 / 非目標

**目標：**
- 申込入力画面のデータを申込内容確認画面で読み取り専用表示できるようにする
- ページ間のデータ引き渡しをZustandストアで一元管理する
- 参照画像のレイアウトに準拠した確認画面を実装する
- 戻るボタンで入力画面に戻り、入力内容が保持されることを保証する

**非目標：**
- 申込完了後の処理（API送信など）の実装
- 入力データの永続化（localStorage/DB保存）
- 確認画面からのデータ編集機能
- バリデーションエラーの詳細表示

## 主要な決定

### 決定1：Zustandストアによるフォームデータ管理

**選択**: Zustandストアを導入し、ApplicationInputPageのフォームデータをグローバルに管理する

**理由**:
- 技術スタックにZustandが含まれており、既存プロジェクトの標準アプローチである
- React Routerの`state`経由のデータ引き渡しは、URLリロードやブラウザバックでデータが消失する
- Context + Providerに比べボイラープレートが少なく、既存コードへの影響が最小限
- ストアの状態はメモリ上に保持されるため、戻る→進むのナビゲーションでもデータが保持される

**代替案**:
- React Router `state`: リロードでデータ消失。却下
- React Context: Providerのラップが必要で、既存のルーティング構造を変更する必要がある。却下
- URLパラメータ: データ量が多すぎる。却下

### 決定2：確認画面は読み取り専用のセクションコンポーネントで構成

**選択**: 入力画面のセクション構造に対応する読み取り専用確認セクションコンポーネントを新規作成する

**理由**:
- 入力コンポーネントに読み取り専用モードを追加すると、コンポーネントの責務が複雑になる
- 確認画面はラベルと値のペア表示のみであり、入力コンポーネントとは構造が大きく異なる
- 参照画像のレイアウトは入力画面とは異なる表示形式（ラベル: 値の1行表示）である

**代替案**:
- 入力コンポーネントに`readOnly`モードを追加: コンポーネントが複雑化し、テストも増える。却下
- 共通の表示コンポーネントを作成: 過剰な抽象化。却下

### 決定2a：確認セクションのラベル幅・値幅を申込入力画面と統一

**選択**: 確認セクションのConfirmationRowコンポーネントに申込入力画面のFormRowと同じ`grid-cols-[260px_1fr]`レイアウトを使用する

**理由**:
- 申込入力画面と確認画面でラベル・値の位置が揃うことで、ユーザーが入力内容と確認内容を視覚的に対応しやすくなる
- FormRowは`grid grid-cols-[260px_1fr]`を使用しており、このレイアウトを確認画面でも再現することで一貫性が保たれる
- 現在のConfirmationRowは`inline-flex w-full max-w-[600px]`を使用しており、ラベル幅が可変のため入力画面との位置ズレが生じる

**代替案**:
- 確認画面独自の幅（max-w-[600px]）を維持: 入力画面との位置ズレが解消されず、一貫性に欠ける。却下

### 決定3：確認画面のステップは4とする

**選択**: StepNavigationのcurrentStepを4に設定する

**理由**:
- Step1: 商品選択（HomePage）
- Step2: 意向確認（IntentConfirmationPage）
- Step3: 申込入力（ApplicationInputPage）
- Step4: 申込内容確認（ApplicationConfirmationPage）← 新規

### 決定4：データ型は既存の型定義を再利用

**選択**: ApplicationInputPageで使用している各セクションのデータ型（ContractCourseData等）をそのままZustandストアと確認画面で再利用する

**理由**:
- 型の再定義はDRY原則に反する
- 既存の型はすでにエクスポートされている
- データ構造の変更があった場合、型の修正箇所が1箇所で済む

## リスクとトレードオフ

- **[Zustand未インストール]** → 新規依存関係の追加が必要。ただし技術スタックに含まれているため、既存の合意に基づく追加である
- **[ページリロードでデータ消失]** → Zustandストアはメモリ上のみのため、リロードでデータが消失する。ただし、入力→確認のフロー中にリロードするユースケースは稀であり、必要になった場合はpersistミドルウェアで対応可能
- **[確認セクションの表示ラベル定義]** → コード値（例: `insurancePeriod: '1'`）を表示ラベル（例: `１年`）に変換するマッピングが必要。変換ロジックは各確認セクションコンポーネント内にカプセル化する
